## What was decided

- **v3 was produced by copying v2 and editing**, so the diff is provably scoped
  rather than asserted to be. Three regions move: the actions bullet, one
  output-shape line, the header.
- **The scope constraint is a test.** The span from `# Anchor questions` to
  `# Output shape` is asserted byte-identical between v2 and v3. The Brier record
  is only comparable across the cohort boundary for the parts that did not move,
  so that has to be mechanical — a future editor with good intentions is exactly
  who would widen it.
- **`target_weight` is pinned as absolute, not a delta** (repeat = hold, omit =
  go to zero). Not named in the spec, but v2 never had to be clear about it
  because nothing consumed the field; a delta/absolute confusion in a live
  allocation channel is a silent wrong number.
- **The ±20% bound and reject-whole-never-clamp contract are carried verbatim**,
  with a test asserting the language survived. v3 opens a channel; it must not
  loosen a bound.
- **`no_action_reason` is OPTIONAL in the schema, in both directions** — a
  judgement call inside the spec, flagged to the director. v1/v2 notes carry no
  such key and must keep validating (the eval harness resolves predictions from
  notes weeks old). And it is deliberately *not* enforced-on-empty: voiding a
  note over a missing one-liner would also destroy that note's predictions, which
  is the one thing v3 was required to leave untouched.
- **The consumer reports which instead.** The constructor emits `no_view` +
  `no_view_reason`, falling back to `UNSTATED`. `note_prompt_version` rides the
  plan into the heartbeat, so the v2→v3 boundary is visible in the *order* record
  and not only the eval record.
- **The pre-stated outcome includes two guardrails, not just a success
  criterion**: zero firewall breaches, and *no movement in the predictions
  record* (a step change there is contamination, not a result). Plus an
  honest-null clause — actions appearing but performing badly is a finding about
  the analyst, not a licence to edit the prompt again.
- **The confirm is someone else's instrument.** T-342's independently-built
  channel-liveness registry scores `hypothetical_actions` NEVER_ALIVE 0/17 vs
  `predictions` LIVE 17/17 in the same files. Its flip to LIVE is the evidence v3
  worked, which avoids self-grading by construction.

## What was learned

- **The v2 file on disk hashes to `6459f11ab60277ae…`, exactly the
  `prompt_sha256` stamped in the real 2026-08-14 note pulled from S3.** That is
  now pinned by a test: the revert target is provably the artifact that ran in
  production, not a drifted copy of it. Worth doing for any frozen revert target.
- Prompt prose is hard-wrapped, so assertions on wording must collapse whitespace
  first — otherwise the test breaks on a re-wrap, which is not what it exists to
  catch. Two of my own tests failed this way before being fixed.
- A hermetic end-to-end run of `run_daily_note` is not cheap: `build_bundle`
  performs real I/O and times out. The service path is already covered by the
  existing 292 analyst tests; the v3-specific risk (prompt load + sha stamping)
  is verifiable directly and was.
- The `test_alphaengine_pipeline` failure flagged on 2026-08-15 as pre-existing
  has been fixed on main since. The suite is now fully green.
